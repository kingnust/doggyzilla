DOGZILLA S2 OPERATOR COMMANDS
=============================

This guide is for the reproducible ROS 2 Humble mapping deployment at:
/home/pi/DOGZILLA

The normal workflow needs only one Raspberry Pi terminal. These instructions
use the global "dogzilla" alias, so commands work from any directory. Depending
on the selected mode, the deployment starts Docker, the safe controller,
LiDAR/Cartographer/Nav2, the USB camera, computer vision, RTAB shadow mapping,
or the authenticated web dashboard.


1. LOAD AND VERIFY THE DOGZILLA ALIAS
-------------------------------------

Commands:
  source ~/.bashrc
  type dogzilla
  dogzilla help

Explanation:
  dogzilla is an alias for /home/pi/DOGZILLA/deploy/dogzilla-map. New terminal
  windows normally load it automatically from ~/.bash_aliases. If a terminal
  says "dogzilla: command not found", run source ~/.bashrc once. You do not
  need to cd into /home/pi/DOGZILLA before using any command in this guide.


2. FIRST-TIME OR TROUBLESHOOTING CHECK
--------------------------------------

Command:
  dogzilla doctor

Explanation:
  dogzilla runs the main DOGZILLA operator script through the global alias.
  doctor checks Docker, Docker Compose, the pinned Yahboom base image,
  /dev/ttyAMA0, /dev/ttyAMA1, free disk space, and desktop display access.


3. BUILD THE DOCKER IMAGE (ONLY AFTER CODE CHANGES OR ON A NEW INSTALL)
---------------------------------------------------------------------

Command:
  dogzilla build

Explanation:
  build creates or refreshes the local dogzilla-mapping:humble Docker image.
  It uses the repository's Dockerfile and ROS package source. It does not push
  the image or source code to GitHub.


4. START NORMAL LIDAR-ONLY MAPPING
----------------------------------

Recommended command on the Raspberry Pi monitor:
  dogzilla start

Explanation:
  start launches the hardware bridge, MS200 LiDAR, Cartographer, occupancy
  grid, and RViz together. Display detection is automatic: RViz opens when
  this terminal has a desktop DISPLAY; otherwise mapping starts headless.
  LiDAR-only mode is the stable default and does not need IMU calibration.

Force RViz to open:
  dogzilla start --rviz

Explanation:
  --rviz explicitly requests the RViz mapping window. Run this from a terminal
  on the Pi desktop/monitor. It will fail from an SSH terminal without DISPLAY.

Start from SSH without a graphical window:
  dogzilla start --headless

Explanation:
  --headless disables RViz but still runs LiDAR and Cartographer mapping.


5. CHECK THAT MAPPING IS READY
------------------------------

Command:
  dogzilla status

Explanation:
  status shows the Docker container state and its ROS topics. Wait until /scan
  and /map appear. Docker should eventually report the container as healthy.

Optional live logs:
  dogzilla logs

Explanation:
  logs follows the latest 200 Docker log lines and continues printing new
  lines. Press Ctrl+C to leave the log view; Ctrl+C here does not stop mapping.
  ROS file logs are stored in /home/pi/DOGZILLA/logs/sessions/.
  /home/pi/DOGZILLA/logs/latest points to the newest session.


6. DRIVE THE ROBOT WHILE BUILDING THE MAP
-----------------------------------------

Command:
  dogzilla teleop

Explanation:
  teleop opens the DOGZILLA keyboard menu inside the active container. Use w/s
  for forward/back, a/d for left/right strafing, q/e to turn, and Space or k
  to stop. Press any number from 1 through 9 to change speed live: 1 is slow,
  5 is normal, and 9 is fast. The safe controller clamps speed and stops within
  0.6 seconds after movement keypresses stop. When teleop closes, it returns
  automatically to speed level 1.

Choose a speed explicitly:
  dogzilla teleop 1
  dogzilla teleop 5
  dogzilla teleop 9
  dogzilla teleop slow
  dogzilla teleop normal
  dogzilla teleop high

Explanation:
  Levels 1 through 9 provide gradual speed control. The words slow, normal,
  and high are compatibility shortcuts for levels 1, 5, and 9. High speed can
  reduce map quality or make the robot unstable, so use it only in a clear
  area with an immediate stop available.


TELEOP WITHOUT MAPPING OR LIDAR
===============================

Start controller-only mode:
  dogzilla drive

Explanation:
  drive starts the dogzilla_drive container with only /dev/ttyAMA0, the motor
  controller bridge, and its movement watchdog. It does not expose ttyAMA1 and
  does not start the LiDAR, Cartographer, map generation, or RViz. Mapping and
  drive cannot run together because both need the same controller serial port.

Check it, drive it, and stop it:
  dogzilla status
  dogzilla teleop
  dogzilla stop

Explanation:
  status should report Active mode: drive and show /cmd_vel but no /scan or
  /map. teleop uses the same live speed menu described above. stop sends a leg
  stop command, closes the controller container, and restores the OLED service.
  Because drive mode never opens the LiDAR port, it does not start or stop the
  LiDAR.

Extra drive-mode teleop keys:
  r / f        raise / lower the body by 5 mm
  i / ,        look up / down using whole-body pitch
  j / l        look left / right using whole-body yaw
  c            center pitch/yaw and restore 105 mm body height

Explanation:
  DOGZILLA has no separate powered neck, so the look commands use Yahboom's
  bounded whole-body attitude controls. These keys are available only in
  controller-only drive mode. Mapping, localization, and navigation keep them
  disabled because tilting the body also tilts the LiDAR scan plane.


FIRMWARE REST CAPTURE, REST, AND STAND
======================================

First stop mapping or controller-only mode:
  dogzilla stop

Explanation:
  stop releases the controller serial port. The rest and stand commands refuse
  to run while either mapping or drive mode is active.

Passively capture the real low-battery firmware movement:
  dogzilla rest-capture

Explanation:
  rest-capture selects the dedicated read-only monitor through the dogzilla
  alias. It requires the exact
  confirmation CAPTURE, then pauses competing vendor and OLED serial readers.
  The monitor sends only battery and 12-joint read requests. It never sends a
  movement, action, motor-angle, speed, servo-load, or servo-unload command.

  Use it only when DOGZILLA is stationary on a clear, level floor and already
  near, but above, the 25% threshold. Do not press the physical power button;
  allow the natural low-battery routine to happen so the Pi remains powered.
  A successful raw file appears in DOGZILLA/profiles/captures/ with status
  captured_unvalidated and replay_enabled false. If DOGZILLA is already low and
  resting when the monitor starts, capture is skipped because the movement was
  missed. Mapping, drive, localization, and navigation also arm this recorder
  automatically, changing joint reads from 1 Hz to 5 Hz only near low battery.

Check firmware-rest availability:
  dogzilla rest

Explanation:
  rest is currently disabled. It prints a safety explanation and sends no
  movement or torque command. Public action 1 is not verified as identical to
  the controller firmware's low-battery/power-button rest. A captured and
  validated 12-joint firmware-rest profile is required before this command can
  be enabled safely.

Play Yahboom's animated stand-up action:
  dogzilla stand

Explanation:
  stand displays a movement warning and requires you to type STAND exactly. It
  first reads Yahboom's battery percentage. At 25% or below, or if the reading
  fails, it exits before sending STOP, enabling torque, or starting an action.
  This allows Yahboom's existing low-battery lying-down behavior to remain in
  control. Above 25%, it loads all 12 servos at their current folded positions
  and then runs Yahboom firmware action 2, the animated stand-up sequence.
  Place DOGZILLA on a clear,
  level floor and keep hands clear of every joint. Both commands temporarily
  pause the OLED service while using /dev/ttyAMA0 and restore it afterward.

To view RViz later from a Pi monitor terminal:
  dogzilla rviz

Explanation:
  rviz opens only the RViz window and connects it to the already-running
  mapping stack. It requires a Pi desktop terminal with DISPLAY available.


LOCALIZATION ON THE SAVED test1 MAP
===================================

Start localization from a Raspberry Pi monitor terminal:
  dogzilla localize test1

Explanation:
  localize starts the MS200, the single serial manager, Cartographer pure
  localization, scan-derived /odom, the test1 occupancy map, and RViz. test1 is
  the map name. It loads maps/test1.pbstream as frozen scan-matching state and
  maps/test1.yaml plus maps/test1.pgm as the visible occupancy map. It does not
  start autonomous Nav2 control.

Start the same localization over SSH:
  dogzilla localize test1 --headless

Explanation:
  --headless disables the RViz graphical window. LiDAR localization and ROS
  topics still run normally inside Docker.

Optional calibrated IMU localization:
  dogzilla localize test1 --imu

Explanation:
  --imu enables the corrected IMU stream in addition to LiDAR scan matching.
  It requires calibration/imu.json from imu-calibrate. Do not add --imu until
  imu-check has passed with the physical robot.

Check readiness:
  dogzilla status

Explanation:
  status should show Active mode: navigation and list /scan, /map, /odom,
  /battery_state, and /joint_states. The Compose container becomes healthy
  after these required topics exist.

Initial localization in RViz:
  Use the "2D Pose Estimate" tool, click DOGZILLA's position on test1, hold and
  drag the arrow in the direction the dog is facing, then release.

Explanation:
  This publishes /initialpose. The localization manager restarts only the live
  Cartographer trajectory against the frozen test1 map. Confirm the live LiDAR
  scan sits on the map walls before moving. Unknown cells in unfinished parts
  of test1 remain blocked.

Drive manually while localized:
  dogzilla teleop slow

Explanation:
  teleop opens keyboard control. slow selects the safest initial speed profile.
  In localization mode it publishes through the manual-priority Twist Mux.
  Body height and look keys remain disabled so the LiDAR transform stays fixed.

Stop localization:
  dogzilla stop

Explanation:
  stop halts the legs, shuts down Cartographer, stops the LiDAR motor, releases
  both serial ports, and restores the Yahboom OLED service.


NAV2 PATH PLANNING ON test1
===========================

Start localization and Nav2 together:
  dogzilla navigate test1

Explanation:
  navigate starts everything from localize plus the Nav2 global planner, local
  holonomic controller, live obstacle costmaps, recovery behaviors, velocity
  smoother, and command multiplexer. test1 selects the saved map. Autonomous
  movement is capped at 0.10 m/s linear and 0.30 rad/s angular.

Start Nav2 over SSH without RViz:
  dogzilla navigate test1 --headless

Explanation:
  --headless disables the graphical window. You still need an RViz client or a
  ROS action client to set an initial pose and send goals, so use this only when
  that client is available elsewhere.

Before sending a goal:
  1. Run dogzilla status and wait for healthy.
  2. Set 2D Pose Estimate in RViz.
  3. Confirm the live scan aligns with the mapped walls.
  4. Keep DOGZILLA in a clear area and be ready to press Space or k in teleop.
  5. Use RViz "Nav2 Goal" only after those checks pass.

Explanation:
  Nav2 plans only through known free cells and treats unfinished/unknown test1
  cells as non-traversable. Keyboard teleop has priority over Nav2. All final
  commands still pass through speed clamps, the 0.6-second watchdog, and the
  low-battery movement lockout.


CHECK BATTERY AND JOINT TELEMETRY
=================================

Open a preconfigured shell in the active container:
  dogzilla shell

Explanation:
  shell opens Bash inside the active Docker service. ROS 2 Humble, the built
  Yahboom workspace, and ROS_DOMAIN_ID=12 are already configured.

Show one battery message:
  ros2 topic echo /battery_state --once

Explanation:
  ros2 runs the ROS 2 command-line tool. topic selects topic operations. echo
  prints messages from /battery_state. --once exits after the first message.
  percentage uses ROS units from 0.0 to 1.0, so 0.64 means 64%.

Show one 12-servo angle message:
  ros2 topic echo /joint_states --once

Explanation:
  echo prints one /joint_states message because of --once. name contains the 12
  joint identifiers and position contains the controller angles in radians.

Leave the container shell:
  exit

Explanation:
  exit closes only this interactive shell. It does not stop the running
  DOGZILLA Docker service.


7. SAVE THE FINISHED MAP
------------------------

Example command:
  dogzilla save room2

Explanation:
  save finishes the active Cartographer trajectory.
  room2 is the map name; replace it with your preferred name. Use only letters,
  numbers, dots, underscores, and dashes. The command creates:

    /home/pi/DOGZILLA/maps/room2.pbstream
    /home/pi/DOGZILLA/maps/room2.pgm
    /home/pi/DOGZILLA/maps/room2.yaml

  .pbstream keeps Cartographer's mapping state.
  .pgm is the occupancy-grid image.
  .yaml describes the map image, resolution, origin, and thresholds.

Important:
  Saving finishes the current trajectory. Stop and restart mapping before
  beginning another new map.


8. STOP SAFELY
--------------

Command:
  dogzilla stop

Explanation:
  stop sends ROS SIGINT and allows up to 20 seconds for orderly shutdown.
  It stops DOGZILLA movement, stops the Docker container, sends an additional
  LiDAR motor-off packet, releases the serial ports, and restores the Yahboom
  OLED service. Saved maps and logs remain on the Pi.

If the LiDAR is spinning while mapping is not running:
  dogzilla lidar-off

Explanation:
  lidar-off sends only the MS200 deactivate command through /dev/ttyAMA1.
  It does not start mapping and does not command robot movement.


OPTIONAL: CALIBRATED IMU + LIDAR MAPPING
========================================

A. CALIBRATE THE PHYSICAL ROBOT ONCE
------------------------------------

First make sure mapping is stopped:
  dogzilla stop

Explanation:
  stop releases /dev/ttyAMA0 before calibration. It is safe if mapping is
  already stopped.

Run guided calibration:
  dogzilla imu-calibrate

Explanation:
  imu-calibrate does not start the LiDAR. It sends movement STOP but does not
  unload servo torque. It guides you through six motionless robot orientations
  and creates /home/pi/DOGZILLA/calibration/imu.json.

  The calibration measures:
    - IMU axis orientation
    - gravity direction and acceleration scale
    - stationary gyroscope bias
    - angular-velocity and acceleration covariance
    - sampling rate and timing gaps

Safety:
  Support the body securely with two hands or a padded cradle. Do not place
  the robot's weight on the LiDAR or legs while it is tilted or upside down.


B. START FUSED MAPPING
----------------------

On the Pi monitor:
  dogzilla start --imu

Explanation:
  start launches the complete mapping system.
  --imu selects the calibrated LiDAR + IMU Cartographer profile.
  Cartographer combines corrected IMU angular/gravity information with its
  LiDAR scan-based motion estimate. The command refuses to start --imu mode if
  calibration/imu.json is absent or invalid.

From SSH:
  dogzilla start --imu --headless

Explanation:
  --imu enables calibrated IMU fusion.
  --headless disables the RViz graphical window.


C. VALIDATE THE IMU BEFORE MOVING
---------------------------------

Keep the robot level and motionless, then run:
  dogzilla imu-check 10

Explanation:
  imu-check validates /imu/data_corrected.
  10 is the number of seconds to collect samples.
  It checks message rate, gravity magnitude, covariance, frame ID, timestamp
  ordering, timestamp age, and communication gaps. Continue only if it says
  IMU validation: PASSED.

After it passes, use the same status, teleop, save, and stop commands described
in sections 5 through 8.


CAMERA AND COMPUTER VISION
==========================

Test the physical USB camera without starting the legs or LiDAR:
  dogzilla camera-check 12

Explanation:
  camera-check temporarily opens only /dev/video0, samples 640x480 ROS images
  for 12 seconds, validates timing and frame freshness, then closes the camera.
  It does not move DOGZILLA and it does not create camera calibration.

Install and inspect the pinned object-detection models:
  dogzilla object-model-install
  dogzilla object-model-status

Explanation:
  object-model-install downloads checksum-verified YOLOX-Nano COCO and YOLOv8
  Open Images ONNX models. They run through OpenCV DNN on the Pi. The weights
  are stored locally under DOGZILLA/models and are not committed to Git.

Start safe, camera-only Vision:
  dogzilla vision raw

Useful recognition examples:
  dogzilla vision color red
  dogzilla vision color-track blue
  dogzilla vision face
  dogzilla vision face-track
  dogzilla vision watchdog
  dogzilla vision qr
  dogzilla vision qr-action
  dogzilla vision line
  dogzilla vision line-follow
  dogzilla vision objects
  dogzilla vision floor-hazards

Explanation:
  Normal Vision owns /dev/video0 only. It publishes detections and an annotated
  camera frame, and starts the authenticated Vision Lab dashboard. Modes with
  "action" or "follow" in their name produce proposals only; action output is
  disabled and this service cannot open the robot controller serial port.
  Color may be red, green, blue, or yellow. Object modes require the pinned
  models to be installed first.

Print the dashboard token:
  dogzilla mission token

Change the detector without reopening the camera:
  dogzilla vision-mode face
  dogzilla vision-mode color-track green
  dogzilla vision-mode objects

Verify repeated detection of a real object:
  dogzilla object-check bottle 15
  dogzilla object-check hammer 15 --floor

Explanation:
  object-check requires at least three separate detections at 0.55 confidence
  and saves a JSON acceptance report under DOGZILLA/logs/object-checks. The
  --floor form additionally requires the detected box to meet the configured
  floor-region test. It refuses explicitly armed Vision Control.

Capture spaced raw frames for a future custom model:
  dogzilla vision raw
  dogzilla object-dataset-capture bolt 60 1.0

Explanation:
  This saves 60 raw JPEG frames, one second apart, under
  DOGZILLA/datasets/bolt/unlabeled. It never commands movement. Labeling and
  training are performed later on a desktop GPU or Colab.

Install an exported optional detector:
  dogzilla object-model-custom-install MODEL.onnx MODEL.labels
  dogzilla object-model-yoloe-install MODEL.onnx MODEL.labels
  dogzilla object-model-status

Explanation:
  custom-install validates a fixed 416x416 custom YOLOv8 detector. The YOLOE
  command validates a static-prompt 640x640 YOLOE segmentation export. Both
  perform an offline OpenCV inference before atomically replacing active model
  files. Stop Vision or Mission Mode before installing weights.

Stop camera-only Vision:
  dogzilla stop


EXPLICITLY ARMED VISION CONTROL
===============================

Examples that may physically move DOGZILLA:
  dogzilla vision-control color-action red
  dogzilla vision-control watchdog
  dogzilla vision-control qr-action
  dogzilla vision-control line-follow

Explanation:
  Vision Control is a separate camera-plus-controller mode. It warns before
  opening hardware and requires the exact typed confirmation ARM VISION. It
  accepts no keyboard or external velocity topic, locks movement to guarded
  limits, requires stable detections and valid battery telemetry above 25%,
  and retains cooldown, target-release, e-stop, and movement-watchdog checks.
  Run it only on a clear, level floor under direct supervision.

Disarm and stop immediately:
  dogzilla stop


CAMERA CALIBRATION AND RTAB VISUAL SHADOW
=========================================

Calibrate the camera intrinsics on the Raspberry Pi monitor:
  dogzilla camera-calibrate 8x6 0.025

Explanation:
  Replace 8x6 with the checkerboard's measured inner-corner count and 0.025
  with its measured square edge in metres. Fill the calibration coverage bars,
  click CALIBRATE, inspect the rectified result, then click COMMIT. Closing the
  window without COMMIT leaves the existing camera.yaml unchanged.

Save the physically measured camera mount:
  dogzilla camera-extrinsics --measured X Y Z ROLL PITCH YAW

Explanation:
  X/Y/Z are measured metres from base_link. Roll/pitch/yaw are measured
  degrees. Do not enter guessed values. The command validates the transform
  and backs up the previous camera_extrinsics.yaml before installing it.

Start normal Cartographer mapping plus the passive RTAB visual shadow:
  dogzilla shadow --rviz

Start the same stack over SSH without opening RViz:
  dogzilla shadow --headless

Explanation:
  shadow first starts the normal MS200/Cartographer mapping stack, waits for
  /scan and /map, then starts the calibrated camera and namespaced RTAB-Map.
  It refuses to start until valid camera intrinsics and measured extrinsics
  exist. RTAB publishes no operational TF and cannot command movement. Its map
  is independent from Cartographer's authoritative /map.

Validate shadow mode while DOGZILLA is stationary:
  dogzilla shadow-check 10

Explanation:
  This checks rectified images, exact CameraInfo, scan/odometry timestamps,
  usable LiDAR returns, RTAB processing, and the isolated shadow interfaces.
  Do not begin the route test unless this reports success.

Open the independent RTAB map view from a Pi desktop terminal:
  dogzilla shadow-rviz

Run a supervised closed-route loop-closure test:
  dogzilla shadow-route-check 120 1.0

In another terminal, manually drive the route:
  dogzilla teleop slow

Explanation:
  The route checker is read-only. During its 120-second window, drive at least
  1.0 metre, return within 0.75 metre of the start, and revisit the same
  textured view. It requires a real global RTAB loop closure and rejects large
  odometry jumps. Stop near the starting position before the timer finishes.

Stop mapping and shadow mode, then validate the saved database:
  dogzilla stop
  dogzilla shadow-db-check

Explanation:
  shadow-db-check opens the latest RTAB SQLite database read-only and verifies
  integrity, schema, node data, statistics, and links. Reports and the database
  remain under the corresponding DOGZILLA/logs/sessions directory.


WEB MAP MISSION EDITOR
======================

Do this only after the current map has been saved and mapping has been stopped.

Install required generic object models once:
  dogzilla object-model-install

Start localization, Nav2, floor-hazard perception, and the browser together:
  dogzilla mission test1 --headless

Explanation:
  mission starts the guarded navigation, detection-only camera perception,
  and browser coordinator.
  test1 selects maps/test1 as the active saved map.
  --headless prevents RViz from opening; the browser becomes the map display.
  The command validates all three saved-map files, refuses to replace mapping
  or another active mode, verifies the model checksums and camera, starts Nav2,
  perception, and the web gateway, checks ROS readiness, and rolls everything
  back if startup fails.
  It does not queue a goal or move DOGZILLA automatically.

Print the browser login token:
  dogzilla mission token

Explanation:
  mission selects the coordinator command group.
  token prints the existing access token from .env. It does not restart the
  gateway or queue movement. Open the URL printed by the start command on the
  same trusted network and enter this token.

Check the complete managed session:
  dogzilla mission status

Follow navigation, perception, and web logs:
  dogzilla mission logs

Explanation:
  status displays the managed state, selected map, shared log session,
  navigation/ROS status, web status, and dashboard address. It does not move
  the robot.

Using the editor:
  1. Select Pickup, then click one free map cell.
  2. Select Drop-off, then click one free map cell.
  3. Choose each heading from the fixed compass list.
  4. Check the green Nav2 route preview and distance.
  5. Optionally save the selected point as a named location.
  6. Press Queue delivery only while supervising DOGZILLA.
  7. Use Vision Lab to inspect the annotated frame and detections.
  8. For patrol, save a polygon, preview its generated coverage route, and
     confirm the patrol safety gate is ready before queuing it.

There is no drag-and-drop interaction and map coordinates are read-only. The
gateway validates free space and clearance again before saving or queuing.
Patrol additionally requires fresh detection-only floor-hazard vision and
complete configured dangerous-class coverage. If a required class is missing,
patrol stays locked even though ordinary deliveries and routes remain usable.

Stop the complete managed mission safely:
  dogzilla mission stop

Explanation:
  stop shuts down the browser gateway first, then navigation, releases both
  serial ports, and sends the LiDAR motor-off fallback. If no managed mission
  exists, it leaves manually started services alone.


OPTIONAL ONE-TIME CONVENIENCE COMMANDS
======================================

Install the Pi desktop shortcut:
  dogzilla desktop-install

Explanation:
  desktop-install copies a DOGZILLA Mapping shortcut to the Pi Desktop.
  Opening it runs the normal automatic-display start command in a terminal.

Install the orderly OS-shutdown guard:
  dogzilla shutdown-install

Explanation:
  shutdown-install uses sudo to install and enable a systemd service.
  During a normal Raspberry Pi shutdown, the service runs the safe stop path
  before Docker exits. It cannot protect against sudden battery disconnection
  or power loss, so use normal operating-system shutdown whenever possible.
